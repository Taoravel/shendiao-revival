## 服务93的完整原生纵切

原跳表 `163f1c0` / `163f09c` 的service93目标为 `16375e9`。此分支加载全局 `2945570`，调用 `148c1f0`，失败转 `163761e` 的反馈路径，根本不打开修理界面。

`2945570` 由 `815c90..815cfa` 初始化，`815cd9` 调 `14a1160` 构造，写vtable `22b2900`，RTTI为 `CFactionManager`。`148c1f0` 实际判断：manager+d0非零，并且 manager+d8/+dc 两字均等于全局 `2944564` 对象+30/+34。任一不符返回false。本批**未命名这几个字段为组织ID/场景ID/职位**，也未证明这是服务器全部资格。离线探针直接执行该比较，覆盖允许、d0为零、第一字不等、第二字不等；三个拒绝均未触发打开。

允许后 `16375f8..163760f` 读取完整 NPC key 高/低，push method1，调用 `16299a0`，然后进入真实 `10de1e0`。这个方法真实保存 method到对象+1c0，NPC key到+1b8/+1bc。本探针仅把界面工厂返回值适配为离线对象，并跳过重绘/控件重置；参数存储指令完整执行。工厂真正构造类由已核对的 `16299eb→10dc9b0`、RTTI `CEquipRepairDlg` / vtable `228e5f8` 确认，布局是 `EquipmentRepairSmiple.layout`；没有声称在探针里完整建立CEGUI。

随后在同一离线对象的确认回调子对象+20设置选中物品依赖，执行原 `10dda40`。原回调自己构造 vtable `2276c04` / type `c0413`，搬运刚保存的method1及NPC key，从选中item bean取key91，并在 `10ddacf` 真实调用提交。再执行原marshal `e4cf30` 得到：

`BE32 method + BE64 NPC key + BE32 column + BE32 item key`。

探针NPC key `0x1234567800000093` 高32位非零，未截断；分别注入column1与4，两者均按原字段提交。**column是依赖夹具提供的选中栏位，只证明原搬运，不证明原界面会为所有方法列出这两栏，也不授予该栏的服务器权限。** 160/855也各执行同样的真实存储→确认→序列化，分别保存/提交0和2，没有用共用结构体猜方法值。

付款展示另有新证据：`10dc090` 调 `10dbb20` 报价后，`10dc0fd` 取人物等级、`10dc109` 取选中装备等级。两者都<60时取wallet+c8/cc，否则取+b0/b4。既有 [货币裁定](CURRENCY_DECISION.md) 已用原UI桥证明+c8为绑银、+b0为现金。这里证明原显示/额度选择分支，**尚未证明原服最终扣款策略**；现有普通修理仅现金设计与之有证据差异，应交root统一裁定。不得仅凭该UI字段读取自行修改共用currency policy或隐式消费绑定银。
