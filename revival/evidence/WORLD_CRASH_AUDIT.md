# 临安加载后原生空指针崩溃审计

日期：2026-10-23（Asia/Shanghai）。本批采用 `diagnosing-bugs/SKILL.md` 的“捕获真实故障 → 构建最小可重放红色信号 → 排序假设 → 用一手控制流判别”方法，沿用 research 的原始源码/数据证据约束。未修改生产服务、原客户端或运行态。

## 复现信号与结论范围

实际读取 dump：`../runtime/client/bin/2026-10-23 9-56-57.dmp`。它记录 exception `0xc0000005`，EIP=`0x12a18f3`，读地址=`0x35`，ECX=ESI=0。原映像在该地址的指令为：

```text
0x12a18f0 push esi
0x12a18f1 mov esi, ecx
0x12a18f3 cmp byte ptr [esi+0x35], 0
```

真实 dump 捕获的全局 `[0x29455ac]` 亦为零。ESP=`0x19ee98`，栈 `[ESP+4]` 为返回地址 `0x11e282a`。调用方原代码：

```text
0x11e281f mov ecx, [0x29455ac]
0x11e2825 call 0x12a18f0
```

因此当前故障的直接来源已经确认：`CActivityListManager` 全局实例缺失，场景进入后无空值保护地调用了其实例方法。该指令没有直接读取 HP、MP、物品表或某个角色容器。本次诊断不能据此排除后续其他问题。

最小重放入口：`research_world_crash.py --replay`。已实际执行，以真实 dump 寄存器在离线 CPU 中执行原故障指令，稳定复现对 `0x35` 的非法读，输出 `RED: original fault instruction reproduced its invalid read`。这是当前故障指令层的最小反馈回路，不是整个地图/渲染循环已经离线重放。结果保存在 `world-crash-replay.json`。

## 排序假设及判别

在继续追踪前向主任务提交了三个可证伪假设：

1. 调用方使用一个尚未初始化的全局管理器：预测调用前 ECX 来自零值全局。dump 和 `0x11e281f` 直接支持。
2. SEnterWorld 仅排队创建对象，而紧接的 Scene 消息早到：预测该管理器构造调用位于 SEnterWorld 或其异步任务中。静态直接调用关系没有支持这一特定对象的该预测。
3. 某 RoleDetail 字段影响该对象构造：预测构造前存在角色字段 gate。当前找到的唯一构造路径由服务器时间消息进入，没有发现以 HP/MP 等作为 gate 的证据。

这将修复方向收敛到补齐原生初始化消息，而不是随意填未知角色字段或跳过原客户端空指针。

## 对象身份与唯一构造路径

对象构造器 `0x12a4c40` 写虚表 `0x229de44`，对应 RTTI 类型 descriptor `0x28d68dc`，字符串 `0x28d68e4` 为 `.?AVCActivityListManager@@`。构造器将 `+0x35` 标志、`+0x38` 等置零，并建立原生容器/加载活动配置。

懒创建入口 `0x816430`：若 `[0x29455ac]` 为零，申请 0x40 字节、调用 `0x12a4c40`，再将结果写回该全局。映像中对 `0x816430` 的唯一直接 call 位于 `0x81b558`。

`0x81b558` 所属函数 `0x81b3e0` 接受服务器毫秒时间、保存 u64，并除以 1000 后交给时间转换函数，根据小时等更新时段状态；一般路径在 `0x81b54f` 检查活动管理器并创建。小时 4 / 10 的部分状态还存在额外条件分支，不能把“向入口发包”直接等同“任何状态下都无条件创建”。没有在本批跳过这些分支。

`0x81b3e0` 的唯一直接 call 位于网络消息处理函数 `0x81f570 → 0x81f579`。因此原生服务器时间消息是当前找到的真实初始化入口。

## 确切消息：SGameTime，而非推测名称

| 项目 | 一手证据 |
| --- | --- |
| 类名 | `knight::gsp::SGameTime`，RTTI descriptor `0x2886fdc`，字符串 `0x2886fe4` |
| 协议 type | `0xc0007` / 786439，构造器 `0xd53c70` 于 `0xd53c7a` 写入 |
| vtable | `0x227034c` |
| body | 单个大端 u64，单位毫秒 |
| marshal | `0xe40a40` 调用 `0x7709b0` |
| unmarshal | `0xd53d00` 调用 `0x770650`，读取 8 字节，存对象 +8 / +0xc |
| Process | `0x81f570` 将对象 +8 的地址传入 `0x81b3e0` |

单位毫秒由 `0x81b3e0` 对原 u64 除以 `0x3e8` 后进行本地时间转换的代码确认。服务端应发送真正的当前 Unix 毫秒时间，不能把示例布局测试常数或零当作当前时间。显示给用户的日期继续采用 Asia/Shanghai；时间戳本身不附加时区偏移。

## 原生离线验证

已运行 `research_world_crash.py --replay --verify-time --evidence`：

- 使用原 `0xd53d00 → 0x770650` 解码 `0000019a00001234`，结果为十进制 1760936596020，恰好消费 8 字节，证明 u64 大端字段序列；该常数仅为结构验证样本。
- 在 emulated image 的活动管理器全局为空时执行原 `0x81b54f` 正常路径，控制流确实到达 `0x816430` 创建入口，随即停止；没有替换该缺失对象检查，也没有把假对象写入真实客户端。
- 保存 `world-crash-disassembly.txt`，覆盖真实故障、调用方、懒创建、时间消息编码/处理和对象构造。

为了避免用假资源/渲染环境取得误导性“绿灯”，没有执行完整活动管理器构造或整个时间 handler。完整构造 `0x12a4c40` 还调用 `0x12a4a60`，涉及实际活动配置和其他管理器依赖；该部分需由真实客户端按正确协议路径完成。

## 提交给主任务的具体修复方向

发送完整 SEnterWorld 后，在 Scene 通知前补上原生 `SGameTime(type=0xc0007, body=BEu64(current_unix_ms))`，观察活动管理器是否按原路径构造，再继续 Scene。该建议依据本次缺失对象的真实构造路径；没有以固定延迟代替协议初始化，也没有建议修改原客户端跳过空指针。

若仍失败，优先读新的 dump 中 `[0x29455ac]`、时间 handler 的额外 gate 以及新的 fault 地址，区分同一原因和新的依赖。只重复旧 dump 的单指令重放不会证明服务器修复已成功。

## 当前状态与未验证范围

已确认当前 dump 的空指针来源、对象身份、初始化消息 type/字段、原生 decoder 和创建入口可达证据；本批没有修改或部署修复，未宣称游戏已入图稳定。原始真实回路的最终绿灯仍需主任务发送修订协议后由当前原客户端验证，并保留结果。

未验证：活动管理器全部构造成功、当前小时特殊状态分支、Scene 后所有功能依赖、其他角色属性和原服成长规则、长期地图运行及移动。捕获资料只输出诊断所需地址和寄存器，没有导出 dump 中任意登录凭据或其他字符串。
