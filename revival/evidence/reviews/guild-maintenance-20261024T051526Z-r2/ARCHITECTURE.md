# 服务器架构约束与接入标准

2026-10-23，主策划依据用户明确要求制定：从功能恢复之初采用可分区扩展的商业游戏架构。本文是目标与接入约束；不表示现有运行服已经完成迁移或容量验收。

## 状态所有权

每份可变状态只有一个权威写入者。单个所有者内部顺序执行命令，不同所有者允许独立推进。锁或串行队列的作用域必须写明具体实体；禁止全局世界锁、全服串行玩法队列，以及持有业务锁等待数据库、网络或跨所有者响应。

| Module | 所有者键 | 权威状态 | 对外 Interface |
|---|---|---|---|
| 连接 | connection_id + generation | 协议阶段、RC4/MPPC流、收发序号、发送队列 | 接收字节、排队发送逻辑消息、关闭 |
| 角色 | role_id + login_epoch | 角色在线租约、背包、宠物、装备、任务、货币与成长 | 命令处理、属性快照、幂等资产结算 |
| 地图 | map_instance_id + partition_id | NPC、位置权威、AOI、传送准备 | 加入、移动、离开、交互校验、传送交接 |
| 战斗 | battle_id | 回合、参与者战斗快照、指令与播放确认 | 提交、推进、确认、结束事件 |
| 社交 | role_id / group_id / channel_partition | 好友关系、频道成员、投递索引 | 关系命令、在线查询、逻辑消息投递 |
| 持久化 | 角色数据分片或独立关系分片 | 资产版本、事务、结算凭据、outbox | 有界异步提交、加载、提交结果 |

Module、Interface 和 Seam 按 codebase-design 使用：在连接与玩法、玩法与持久化之间放置 Seam，隐藏路由、数据连接和事务细节。初期可同进程部署；所有权与消息契约保持可跨进程。Python线程只隔离阻塞I/O，CPU密集的世界与战斗执行分区需能迁移至多个进程。接口只在实际依赖处建立，避免空转发层堆积。

## 连接、执行与背压

- 网络循环只做有预算的收发、协议路由和异步等待；数据库等待、配置全表读取、DDL、日志文件打开/刷盘和大批广播均移出网络循环。配置启动时加载为只读快照；表结构迁移启动时统一执行。
- 每条连接的编解码状态与密文输出由同一所有者顺序使用。社交和玩法只投递逻辑消息，不得从其他执行线程直接访问目标 Session 的 RC4/MPPC 或 writer。
- 工作任务不得持有其他 Module 的可变对象；跨所有者传递不可变命令、ID或版本化快照。仅将整个 Session.feed 扔进共享线程池不能完成迁移；当前 SocialHub.push 会访问其他会话，必须同时改为目标连接排队投递。
- 各所有者的邮箱、数据库工作队列和每连接发送队列有明确容量及满载策略。可靠结算命令拒绝/背压并保留重试键，位置更新可合并为最新版本。慢连接可断开，不得拖住整个地图广播；广播按AOI筛选并分批发送。
- 每个角色只允许一个有效 login_epoch；断线重登、连接替换、关服停机均使过期回调失效。请求有 request_id、deadline，取消等待不等于撤销已经提交的资产交易。

## 交易、奖励与跨区

- 同一角色的任务奖励、背包、宠物、货币和经验变化经角色所有者提交，在一个数据事务中同时写入资产及幂等凭据。重试返回既有结果；跨模块各自开连接提交不具备这项原子性。
- 战斗基于版本化属性快照运行，结束产生唯一 settlement_id。角色所有者校验参与资格并结算；战斗 Module 不直接改背包或任务数据库。
- 跨角色交易采用专用交易状态机，以稳定角色ID顺序预留资产、提交或补偿；避免互相同步等待两把角色锁。跨分片交付采用事务 outbox/inbox、去重与可恢复状态，目标为至少一次投递下的幂等效果，不宣称网络恰好一次。
- 跨地图传送采用预留目标→冻结源移动→切换带版本的归属→确认后清源的交接协议。失败恢复有唯一权威位置，旧地图事件不得覆盖新位置。
- 移动状态按角色与位置版本合并检查点；关键传送/登出提交明确持久化策略，不把每一格移动都变成同步写库。

## 存储与故障隔离

SQLite 仅保留为本地兼容 Adapter 与验证环境。所有写者共享一个SQLite文件时仍有文件级单写瓶颈；WAL改善读写并行，不能称为多写扩展。商业部署采用支持并发事务的数据库，按角色键路由并索引；数据分片与跨角色结算协议同时规划。

数据库连接和事务封装在持久化 Adapter 内，经有界执行资源异步访问。不同地图/战斗的执行不能共用一条阻塞工作队列；数据库故障触发局部超时、背压和恢复，禁止把未落盘奖励回报成已成功。角色热路径不做schema变更和重复全表解析。日志独立有界排队；结算审计可靠记录与普通诊断日志分开处理。

记录各分区邮箱长度、命令等待/执行时延、事件循环延迟、数据库排队/事务时间、发送积压、超时和重试数量，并以 role_id/battle_id/map_instance_id/request_id 关联。容量和并发性能只有实测后才能宣称。

## 初始缺口与当前窗口分工

初始静态审查发现：原`serve.py`在事件循环中同步调用Session.feed，下游直接连接SQLite并提交、日志同步写盘，热路径可建表和加载大配置，SocialHub持有Session并直接push。这些是迁移前的缺口，不能再据此描述当前新入口。第一阶段GameRuntime源码入口及双连接慢I/O隔离已接入并验证；最新实际路径、部署与剩余限制以 `evidence/RUNTIME_INTEGRATION.md` 和主策划 `evidence/ARCHITECTURE_ACCEPTANCE.md` 为准。商业数据库、多进程部署、完整容量验收仍待完成。

原始复原聊天负责共享入口迁移：`serve.py`、`gateway.py`、`accounts.py`及实际执行/持久化适配。各系统窗口继续恢复原生协议与独立领域逻辑，通过上述契约提供接线；共享文件当前编辑收敛后交由集成方统一修改。主策划在本聊天维护裁定与跨系统验收。

接入顺序：先移出阻塞I/O并建立连接发送所有权，再将角色和地图状态从Session拆出，接入战斗独立所有者和幂等资产结算，最后验证分区并行与故障恢复。恢复原生资料与纯领域逻辑可继续并行，新的运行时功能按所有权契约接入。

## 必要验收

1. 慢写库或慢日志期间，另一角色的心跳、另一地图移动和另一场战斗能继续处理；用受控阻塞释放事件证明独立推进，并设置有界超时，不能只查有没有Lock关键字。
2. 同角色冲突操作串行且扣款一致；不同所有者能独立推进；同一结算键重试只生效一次，提交后断线重登结果一致。
3. 发送积压和邮箱达到容量时按策略背压/拒绝；断线后旧epoch回调不能发送或改新会话状态；原生加密/压缩流顺序保持一致。
4. 架构交付写清已迁移路径、仍同步的路径、压测条件与实际结果。只通过资料提取或协议解码的功能，状态保持为尚未完成运行时接入。

## 本批记录与依据

方法：codebase-design用于所有权和Seam划分；writing-for-agents用于将约束、接入顺序和可判定验收写入项目入口。产物：本文、根AGENTS指针、主策划文档指针以及各窗口交接。本文初始验证为静态读取核心路径和核对官方并发文档；后续运行时实现、真实监听与验证记录按上述指针维护，避免本文缓存过时的运行状态。商业容量与完整可玩性仍未证明。

[Python asyncio官方说明](https://docs.python.org/3/library/asyncio-dev.html)说明事件循环中运行的阻塞工作会延迟其他任务，以及跨线程调用须遵循线程安全调度；[SQLite WAL官方说明](https://www.sqlite.org/wal.html)说明单库同一时刻仍仅有一个写者。这两项限制决定本项目不能将“没有显式全局锁”当作架构验收。
