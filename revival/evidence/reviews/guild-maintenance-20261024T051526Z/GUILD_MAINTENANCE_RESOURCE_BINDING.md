# 帮派维护资源、资金与研究力：原生字段绑定

调查日期：2026-10-24。对象为本地1.6.1端游、network601的离线映射镜像。第25批研究子任务；唯一产物为本文。未修改实现、共用policy或其他文档，未访问服务、游戏进程、真人库或存档。

## 可供实现采用的结论

1. `client_verified`：帮派详情的“剩余资源”是原详情bean偏移`+0x58`的一份32位标量，经manager`+0x2e0`进入主帮派窗口`Gang/GangDetail/Gangresource`。它与资金、研究力、维护费分开存储；布局明确说正常维护增加、成员学习技能消耗。
2. **尚未证明该资源就是七项现金修炼消耗的“资材”。** 现有`guild_practice_materials.available`的预留/退款账，不能因为两个中文名称相近而接收本次维护产出。本批没有找到七项现金修炼购买消费者读manager`+0x2e0`的路径，也没有证明二者原版必然不同。实现上继续分账属于保守的`designed`接缝，不应宣称恢复了二者原始关系。
3. `client_verified`：研究力是bean`+0x5c`的32位标量，资金是`+0x48`的64位量，维护费显示值是`+0x60`的64位量。原生离线执行证实这些值经过接收、快照复制、UI数字格式化实参保持一致。**这里证明的是服务端供给字段的消费者，不是建筑到数值的计算公式。**
4. `client_verified`：原主窗口比较资金与`48 × 当前显示维护费`。离线执行证明小于为红色，等于及大于为白色；不能据此证明实际服务器在扣费前或后判定、基本维护扣多少或维护费已经如何包含低人气加成。
5. `client_verified`：人气bean`+0x78`是显示当前值，也是UI的1000阈值输入；`+0x7c`是`当前/分母`显示的分母。将分母进一步命名为服务器硬cap仍属`inferred`，没有执行容量约束函数。
6. 正常维护费、独立基本维护费、工坊资源刷新量/上限、练功房研究力/每小时研究XP、聚义厅资金存储上限，**本批均未找到有实际消费者绑定的计算函数或数值表**。仍需唯一设计来源裁定，不采用个人`clifeskillcost`作为研究曲线，也不采用布局预览值。此结论限于实际追查范围，不是证明整个原客户端绝无这些函数。

### 接收、快照、格式化数值输入

在原消费者入口`ESP+4+bean偏移`放置各不相同的夹具：资源12345、研究力6789、人气999、显示分母5000、资金`2**40+113`、维护费`2**35+17`。从`0x14a34f0`运行，唯一跳过的外部边界是`0x14a3598`的头部字符串复制：在call指令之前弹掉已push的4字节参数并将EIP移到`0x14a359e`，在`0x14a3688`停止。该适配不改任何数值复制指令。实际manager结果如下：

| 夹具量 | manager实际结果 | snapshot实际结果 | 原UI格式化实参 |
| --- | ---: | ---: | ---: |
| 资源 | 12345 | 12345 | 12345 |
| 研究力 | 6789 | 6789 | 6789 |
| 资金 | 1099511627889 | 1099511627889 | 1099511627889 |
| 维护费 | 34359738385 | 34359738385 | 34359738385 |
| 当前人气 | 999 | 999 | 第二次32位调用999 |
| 人气显示分母 | 5000 | 5000 | 第一次32位调用5000 |

快照切片执行时设ESI为目的对象、EDI为manager`+0x228`；再将实际快照对应数值放到原UI切片的原局部偏移运行。到`0x847450`或`0x490220`入口截获实参并停止，未用自写格式化替代数值装载。这证明高32位没有截断；没有测试负值或业务上限，因此不从此推导负数合法性。

### 原48倍比较的边界

从`0x14b12f9`运行，EBX=0对应原函数已建立的零常量。原`0x1919610`的64位乘法也实际执行，格式化边界只返回一个假字符串指针，运行到`0x14b1364`截获将传给控件的颜色。维护费使用100000001，乘积超过32位，结果如下：

| 资金 | 与48×维护费关系 | 实际控件颜色 |
| ---: | --- | --- |
| 4800000047 | 少1 | `0xffff0000`，红 |
| 4800000048 | 相等 | `0xffffffff`，白 |
| 4800000049 | 多1 | `0xffffffff`，白 |

原指令对64位的高半作有符号比较、低半作无符号比较；本批仅验证正值正常范围。该UI逻辑支持“资金不足48倍”中的严格小于边界，**并未执行实际服务端正常/基本维护判定**。

### 原人气输入与1000边界

从`0x14b1460`分别用当前999/1000、分母5000执行，第一次32位格式化都收到5000，第二次分别收到999/1000。只在第一次格式化边界返回假字符串指针，第二次截获后停止。静态追踪表明随后以红/白当前值、白色斜线和分母拼接；原比较常量为1000。未把这个UI变色执行称为“低人气维护费+50%计算函数”。

## 方法、设计建议及未验证范围

本批按用户Matt Skills要求使用`research`：先读项目设计权威及既有原文报告，追原bean复制、真实控件名称、数字读取到实际执行输入，不用词相近或表名相近推断账本。使用`codebase-design`：把复杂字段映射和维护计算留在帮派Module Implementation，调用Interface只接当前帮派/小时/来源凭据，调用者不传可信费用、产出或任意研究经验。

`inferred/designed`架构建议：资金、人气、独立维护资源、建筑、维护时钟与小时凭据归同一帮派Owner，正常/基本费判定、扣费、产出及同事务研究推进由同一事务完成；其对外Interface隐藏cap及分支算法。现有七项修炼资材独立保留，不给本批维护生产者第二个未经证实的写入目标。新帮派基线须明确版本化设计，历史缺档不自动填0或套新政策。本报告没有裁定具体生产数值或授权迁移。

已读`ARCHITECTURE.md`、`DESIGN_AUTHORITY.md`及研究/建筑/资材既有报告。实际验证为离线原生切片执行、布局/名称/反汇编交叉绑定、三个48倍边界、两个人气边界、字段宽度和文件SHA。未运行真实GUI、完整详情编解码往返、真实NPC购买、服务端小时任务/容量测试或原服维护；未证明当前资材与维护资源的原版相等或不相等；未审计原包CRC或穷尽所有资源/代码。未改共享入口、实现、正式设计表或服务。
