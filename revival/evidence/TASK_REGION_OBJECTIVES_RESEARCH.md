## 结论

1. **type56原到区判定使用ActiveInfo四边×16后的坐标，与角色当前位置比较：`left*16 <= x < right*16`，`top*16 <= y < bottom*16`。** 左/上包含，右/下不包含。地图必须精确相等。[N1、P1]
2. **到区命中实际发送CCommitScenarioQuest0xc4a44：taskID、npcKey0、option0。不是CQuestReachScene。** 同一原函数按活动链表顺序找首个命中项，每次最多发一项；没有本地消费任务/去重，未更新状态前再次轮询可重复发送。[N1、P1]
3. **CQuestReachScene0xc4a54确为空body，但所定位发送点属于场景进入reason516018(0x7dfb2)的特定分支，不是通用“进入某个任务矩形”报告，也不是普通换图ready。** 空体不包含任务ID、位置、地图或交接身份。[N2]
4. **零边界没有wildcard特殊解释。** 左/上0可正常作为包含边界；全零矩形是空区域。原102626恰为map0、四边0、AnimationID60019，即使模拟当前map0、位置0/0也不会经本轮询命中；它的原其他触发机制未证实，不能设计为“任意地图立即完成”。[S1、N1、P1]
5. 183条中13条有AnimationID、170条无。**同一个到区轮询不读取AnimationID，带动画样本也发送相同CCommit。** 这只证明上报判定相同，不证明服务端可以忽略后续剧情/换图时序，也不把这些AnimationID统一当CG。[S1、N3、P1]

本文不裁定服务器何时完成任务、是否主动按位置完成、如何在重连/重试时选择或结算多个任务。客户端命中/上行都不能代替服务端权威位置、地图、任务阶段、租约与幂等事务校验。

比较是原signed32分支，原表非异常小坐标范围内可写成半开矩形：

```text
same_map && L*16 <= x && x < R*16 && T*16 <= y && y < B*16
```

未对任意负数/超大整数、溢出或未加载地图做通用支持承诺。

### 首个命中项与实际包

不命中时 `0x1257eb4` 取当前链表节点next，继续扫描。命中时直接转 `0x1257ec1` 构包：

```text
type = 0xc4a44 (CCommitScenarioQuest)
body = BE i32 task_id | BE u64 0 | BE i32 0
```

`0x1257ec3/0x1257ecb` 写vtable0x227d670/type；`0x1257efa–0x1257efd` 把首个命中的节点taskID填进对象；`0x1257f01/0x1257f05` 明确npcKey两半为0，末字段先前已置0；`0x1257f1a` 发送后到函数收尾，不扫描其余命中任务。

该代码没有按任务ID排序、没有优先级比较、没有就近选择、没有AnimationID筛选、没有bean.state检查。它使用的是本地活动链表的当前迭代顺序；本文不把此顺序硬称为原服任务优先级或所有重登情形的接取顺序。服务端更不能用客户端列表状态代替权威失败/完成阶段判断。

该路径也不删除本地任务、没有已发送标记。P1保留同一列表再次调用会再次发送同一taskID。因此服务器需自行处理重复意图；如果同时多个任务都满足，客户端可能反复报告首项，不能把“未收到第二项请求”当作第二项不在区域内。
