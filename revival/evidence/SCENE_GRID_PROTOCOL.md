## maze.dat 结构及坐标：client_verified

原生加载链 `0x11e0310 → engine虚表+0x48 → 0x5f9770 → 0x5fcd50 → 0x672ff0 → 0x672720 → 0x672490`。场景构建时 `0x11e03de` 拼接 `/maze.dat`。

`0x672490` 校验：文件至少12字节；首 uint32 必须 >=12；文件总长必须是 `first_uint32 + width*height`（第二、第三uint32）。原始数据指针设置成 `buffer + first_uint32`。因此首值12在原生实际充当**头部字节数/数据偏移**；仅凭原包都为12不能断言它仅为格式版本。现有 `maze_grid` 只接受本包的12字节头，保持这个严格包内约束可以，但名称 `format_version` 并非原生语义证实。

差分执行 loader 的未改动校验段，12字节头和合法16字节扩展头均被接受；小于12或总长不符被拒绝（5例）。为避免原版后续复制指令访问模拟之外的对象，测试在校验成功 `0x6724cf` 停止，未声称整个资源加载过程已执行。

`0x6284f0` 为原生单点网格判断，输入 `EAX=x`、栈参数包装对象及 `y`；包装对象+4指向8个整数的查询布局：`width, height, cells_pointer, mask, min_x, min_y, max_x, max_y`。它将有符号x和y分别**向零除16**，验证查询范围，取 `cells[y*width+x]`，若字节与 mask 的低8位无交集则返回 true，越界返回 false。负坐标 -1..-15 会按原生变为0，故 `maze_clear` 本身不是服务端负坐标合法性校验器，地图Owner仍须先做位置边界检查。

[纯查询实现](../world_collision.py) 和原生对11个mask、256个flag值及负值/边界坐标进行2,893例差分，全部一致。Interface 要求显式 mask，不提供推测默认值。它只实现全网格查询，未实现原生局部 min/max 矩形或直线路径查询。

`0x11e0386` 的水平投影乘数位于 `0x2923784`，渲染格24×16；它不能直接替代逻辑查询的16×16。调用者需在既有协议坐标体系内传原生逻辑像素。此查询不对网络坐标自动乘1.5。

**首批尚未证实（本轮下文已补充角色状态选择链）**：普通步行、飞行、跳跃、船只各选何mask；0、3、8、11等flag的每一位的美术/玩法名称；拐角及连续路径穿墙语义。禁止把 `mask=3` 或 `mask=8` 当原版默认，也不把仅有端点检查称为连续路径碰撞恢复。后续应从移动状态选取mask的调用处核验，再由地图Owner使用。

## monster.dat 与 CMineAreainfo：结构已取出，映射未证实

44个文件按 `<4I>` 头（首值16、声明宽高、记录数）后跟每条5字节 `<HHB>` 解码；观察字段顺序为y、x、原始byte。该顺序的字段名称来自原始位置分布及现有解析，**本轮尚未找到消费此文件的原生函数，不能称原生执行证明**。主线程 `world_grids.MonsterRegions.records` 保留顺序、重复及声明尺寸之外的坐标。

12个文件存在重复坐标或声明范围异常。雷峰塔5/6/7层各3024条记录越过声明范围；不得裁剪、静默末条覆盖或把异常文件当空区域。具体数量见 [machine-readable结果](scene-grid-native.json)。

本地 `knight.gsp.map.cmineareainfo.json` 包含 id 0..48及colour/discribe；0描述“清除刷”。但monster原始byte集合除了0..48的部分ID，还包含244、245、246、249、250、251、252、253、254、255。**这些值无同ID配置行**。它们可能含有符号标记/编辑数据，但本轮没有确定解释。不能直接把全部byte联到CMineAreainfo产生怪物，更不能把byte本身当NPC或怪物模板ID。

原生映像中搜索ASCII和UTF16的 `monster.dat` 均未命中；这只说明本映像无此明文常量，不证明服务端或其他DLL不会读取。CMineAreainfo RTTI存在，单靠表名不够确定区域触发/怪物数量/概率。还需要消费代码或原服配置把区域接到 encounter/battle/monster 的证据。

方法：重读 diagnosing-bugs，沿用第一批2,893例原生差分作为确定反馈；此子任务研究未明的原生选择逻辑，无已报告的确定崩溃/错误场景，故不把“原版未知”包装成可复现游戏bug，不宣称其完整修复流程完成。research 追到每层原生所有者代码。没有打开游戏、GUI、重登或重启。

本轮对“3/8固定默认”“角色状态动态选择”“底层查询自带默认”三个候选进行调用链排查。证据确认第二种；底层query仍必须传mask，角色实例按状态安装mask，不能覆盖整个世界的统一模式。

已证实的具体链：

1. RTTI `.?AVCCharacter@@` 原始虚表 `0x2298bcc` 与 `.?AVCMainCharacter@@` 虚表 `0x2299344` 的+4槽均指向 `0x1209d10`，读取实例 `byte+0x218`。
2. `0x12028f7..0x1202919` 真实调用该getter，`neg al; sbb eax,eax; and eax,7; add eax,1`：状态byte为0选mask **1**；任意非0选mask **8**。它随后通过角色 `+0x26c` 指向的actor虚表+0x184安装mask。
3. actor原始虚表 `0x2462544` 的+0x184槽是 `0x652af0`，从actor+0x1a8取寻路对象，再写其+0x48。没有主机代码替代此setter。
4. `0x6bc2f0` 内 `0x6bc33d..0x6bc340` 将寻路对象+0x48写到地图查询布局+0xc；`0x6bc3d9..0x6bc3ff` 经 `0x6138d0` 传该查询布局，后者通过 `0x626b40` 的线段采样进入 `0x6284f0` 单点判定。另一条路径在 `0x6bc65d` 也安装相同mask。
5. 角色状态更新路径 `0x120cfd5..0x120d038` 同样重新读getter，并按0→1、非0→8安装mask；不是只在创建时选一次。
6. `0x11f5e20` 还明确把另一个实例的布尔状态+0x40转换为8/1，经虚表+0x130传播；这些片段支持状态切换逻辑，但本轮未给+0x218的玩法名。

已新增 `character_movement_mask(state_byte)` 纯Interface，严格按0/非0选择1/8。**没有**把 `state_byte` 直接改名为 `flying` 或 `ordinary_walking`：仍需将协议角色状态或正常初始化实际绑定到+0x218。可判定“该角色原生状态为0时mask=1”，不能以此宣称船、跳跃、骑乘等每种模式均已恢复。若集成方目前只恢复普通非特殊状态，选择1应明确附上“状态+0x218=0”的前提，避免用以前无证据的3替代。

可执行反事实：同一个模拟角色、原始虚表和原始setter，仅将角色+0x218改为0/1/2/255，分别得到1/8/8/8，并执行未修改的 `0x6bc33d` 证明查询布局+c接收到同一值。这4例与原有2,893查询差分共同通过，见 `character_mask_native_cases`。对flag=1与flag=8，两种模式的判定结果相反；错误交换/固定mask会被现有全flag差分和新增选择断言捕获。

## 第三批：原生直线段判定与报文列表来源（2026-10-23）

方法：research沿原调用链定位 `0x626b40`；diagnosing-bugs使用可确定差分反馈，先以原生样点轨迹和返回分类为判定，再编写纯实现；codebase-design将定点运算封在原有碰撞 Module 后。代码不涉及世界状态/数据库/网络，无客户端、GUI或服务启动。

### 段判定：client_verified

新增Interface：

- `maze_segment_result(grid, start, end, *, mask) -> int`：原生0表示通过、1表示样点遇阻、3表示起终相同。
- `maze_segment_clear(grid, start, end, *, mask) -> bool`：原生0/3为true、1为false。

原生 `0x626b40` 接收 `EAX=end_x, EDX=start_x, ECX=start_y`，栈参数 `end_y` 和双指针查询包装。后者+4指向第一批已有的maze布局。它不调用任何宿主库，以原16.16定点DDA逐个**主轴像素**调用原生 `0x6284f0`。横纵差绝对值相等时选x主轴。斜率为原x86 `idiv` 的向零整数商；商为负另加1。正向第一样点次轴累加斜率及 `0x7fff`，反向减斜率再加 `0x8000`；每轮32位溢出、算术右移均保留原语义。这是像素采样，不是格子Bresenham或supercover。

起点**不采样**；终点包含。同点原生直接返回3，完全不查询maze。调用方必须先分别做权威起点、报文节点和最终点检查。不能以 `maze_segment_clear` 同点true跳过节点合法性。纯实现限定原协议signed-short坐标，从而单调用最多65,535样点，不引入无界枚举；运行时还应按本地图/命令预算限制段数及跨度。

[复现程序](../verify_scene_segments_native.py) 在Unicorn中运行未修改的段和点查询指令，仅在0x6284f0入口观察真实样点，不替代判定。固定种子601，143条段（四方向、斜率、负值、同点、128随机），各用mask1/8，遍历16格单独放墙并另测无墙，共4,862例；纯实现返回值及采样轨迹与原生一致。[结果](scene-segment-native.json)、[原生段反汇编](scene-segment-native-disassembly.txt)。

3个明确反事实均实际执行：

- 起点(8,8)与终点(56,8)均清，但中途格(1,0)设阻挡：原生返回1，证明只查两端会漏墙。
- (8,8)所在格阻挡，起终同点：原生返回3且样点空，证明原同点捷径必须配合独立点校验。
- (8,8)→(24,24)斜对角经过角点；格(1,0)/(0,1)都阻挡，但对角格清：原生返回0。不得额外发明“邻边任一阻挡禁止过角”并称原版规则。

4,862例反事实足以验证此函数，但不构成完整A*、跳跃/船只特殊处理或客户端整段行走实测。正反方向有不同定点偏置，调用者必须保持真实段方向，不先排序端点。

### +340的首点和顺序：原getter确证

actor虚表0x2462544+0x174的函数是0x652a70，调用0x6bc6c0。该函数先清输出，再将寻路对象+0x2c的未来节点按原顺序复制；随后0x6bc6fd..0x6bc746以当前寻路坐标+8/+c生成一个点，并**头插**到输出。X先对投影float向零截整，再除1.5截整；Y对float向零截整。

原getterfixture：当前(8,8)，未来[(56,8),(56,56)]，实际输出[(8,8),(56,8),(56,56)]。继而执行原0x1214aa9..0x1214b94，只有(8,8)进入+34c，未来两个点留在+340。因此ROLE_MOVE发送后立即记录的首点是这次路径开始的当前位置，**不是首段目标已到达**。ROLE_MOVE另一坐标仍为意图，不能从当前位置对其直接做“已走段”判定。

### 后继节点何时进入历史：实际engine→App→Scene→MainCharacter

寻路对象tick0x6bc7a0计算本帧预算与到未来队首的距离。未达到时在0x6bc979..0x6bc9d2插值更新当前位置；预算越过节点时0x6bc932..0x6bc95e先将当前位置设置为队首，0x6bc961调用0x6bc5e0删除引擎未来队首，并通过工厂+0x54取得事件接收器，发送(actor指针,1)。工厂getter0x5a62b0读取+0x28；原映像该对象为应用0x2945060，虚表0x224db3c+0x20=0x81c670。

### 真实CHECK、STOP和连续两个上报

直接运行完整CMainCharacter::0x12171d0和0x1217f00，保留原constructor、链表复制、虚拟sender调用和清理指令；使用空/两点历史共4例。CHECK将+34c完整按顺序复制，发送后清+34c，保留+340未来规划。STOP同样复制历史及当前点，发送后清+34c，并清+340的剩余规划，**不会把取消的未来规划点当历史发出**。外层0x1218000随后调用0x1206080停止actor；单独0x1217f00只清角色侧规划，不能据此宣称引擎队列也已停止。

又以同一原引擎连续执行：开始(8,8)→到首拐点后CHECK，真实历史[(8,8),(56,8)]、当前(56,9)；再次行走到下一拐点后STOP，真实历史只有[(56,56)]、当前(54,56)。这支持普通情况下服务端按上一次已受理CHECK/STOP的当前位置，接续本次历史节点，最后接本次current的折线顺序。首次可含与权威起点重复的初始点；相邻重复点应独立点检查后按原DDA同点返回3处理，不凭重复坐标推断恶意。

### 权威起点接续、重报及量化限制

- 原客户端发送后立即清历史；它不等待服务器ACK再删，也没有从该builder发现跨报文重复发送整个旧history的机制。故正常同连接有序CHECK/STOP应接上一次**已受理的报告current**，不能把先前ROLE_MOVE目标当权威起点。真正的重放、重复命令、旧租约或换图前残包须由Owner的版本/幂等/场景防护处理，客户端列表本身不能证明新鲜性。
- 不可按“找列表中等于权威点的最后一个位置”盲目丢前缀：合法路径可能折返或多次经过同一点；本批没有原服ACK/重传归并算法证据。若实现另行裁剪旧历史，须有明确的已受理命令/代次凭据并标designed，不能仅靠坐标推测已处理。

### 特殊模式和接入条件
