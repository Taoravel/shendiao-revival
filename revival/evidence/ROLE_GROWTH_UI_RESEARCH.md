# 人物升级与普通世界属性显示研究

2026-10-23；目标为本地端游客户端 1.6.1 / 网络版本 601。只读原资源和既有原生映像；没有操作客户端、注入、发包或运行战斗。本轮仅写本报告。

## 可交接结论

- `client_verified`：普通世界 **SRefreshRoleData，type `0xc32c8`** 接收 `map<i32,float32>`，键 **490** 刷新人物等级；本轮所列五维、派生、生命/真气和潜能键由同一普通处理器写入人物属性 map，无须借用战斗初始化包。
- `client_verified`：人物自由潜能的显示键是 **500**。原人物入场处理器和人物 UI 都使用这个键，结论独立于宠物。
- `client_verified`：现有 `world_protocol.world_snapshot` 的 `32i` 前五槽确为 **60 当前生命、640 当前生命上限、140 生命最大值、70 当前真气、150 真气最大值**。可接入调用方明确提供的 profile；五槽数值本身不是原版出生/升级恢复规则。
- `client_verified`：**SLevelUp `0xc000a` 的 process 为 `ret 8`**，不能指望它更新等级；等级刷新采用上述 490 map 路径。升级后自动回血、伤势上限如何恢复、自动/手动升级以及潜能发放量仍由既有主策划设计决定。

## 普通属性刷新协议和等级写入

SRefreshRoleData：RTTI `0x28c197c`，vtable `0x22832ac`；构造 `0xec35c6` 写 vtable、`0xec35f0` 写 type `0xc32c8`。payload 为一个属性 map，无角色 ID、无额外等级字段：

1. `0xec36b0 / 0xec3730` 为 marshal / unmarshal；`0xec1310` 建立 map codec，vtable `0x22831f4`。
2. map marshal `0xec1890` 以 compact 写数量（调用 `0x770bf0 → 0x7706b0`），逐项调用 `0xec1800`；每项是 **BE i32 key + BE IEEE-754 float32 value**。`0xec1845` 对 value 用 `fld dword`，随后将 float 位模式 `bswap`。unmarshal `0xec1e20 → 0xec1420` 对每项读两个 BE32；第二个随后按浮点消费。
3. validator `0xec3630` 仅检查各 key > 0，本轮未见要求 value > 0；所以有效的 0 属性/0 潜能不应因“零值”被丢弃。
4. process **`0x113f070`** 要求全局 `0x2944550 / 0x2945560 / 0x29455cc` 均存在，否则直接返回。这是已进入正常人物世界所需上下文，不能把静态消费证据等同于任意时点发包有效。
5. 人物对象取全局 `0x2944550`；`edi = role + 0xf8`。对每个键，公共尾部 `0x113f60e` 读取 float32，调用 `0x19191e0` 转整数；`0x113f619..0x113f62e` 用键查/建 `edi+0x6c = role+0x164` 的整数属性 map，写入**绝对值**。不是增量相加，也不是把 float 原始位模式作为整数存入。
6. 处理完 map 后，`0x113f6e0..0x113f714` 触发人物通知链（role+4 的虚调用，以及 role+0x2b0 容器经 `0x11335a0` 调用回调 `0x10876d0`）；另有条件下的 role+0x14 通知。这里证明有共享通知，不宣称逐一验证所有 UI 面板的 observer 注册。

**等级490专分支**：`0x113f134` 比较 key `0x1ea`；`0x113f160..0x113f189` 将 float 转整数并写入全局等级对象 `[0x2945644]+4`，同时置本批“等级变化”标记。`0x113f230..0x113f26d` 写上述属性 map；公共尾部再次写同键。`0x113f6b1..0x113f6da` 从属性490取当前等级，调用 `0x89e660` 的原人物经验表 getter，以该等级为键读取配置 `+0x10/+0x14`，写 `edi+0x90/+0x94` 的下一等级经验门槛。最后 `0x113f75b` 调 `0x1139170` 做等级后续通知。人物 UI `0x114b50a..0x114b529` 同样读取490并查当前等级配置。

有1000段等级显示分支，但本轮不解释该段业务，不据此修改普通升级索引。普通等级应传真实已提交等级，不能只刷新经验或只发一个升级提示。

**排除 SLevelUp**：vtable `0x2270404`，构造 `0xd54470`、type `0xc000a`，marshal `0xe40d60` / unmarshal `0xd54510` 仅有 object+8 的单 BE32，构造默认0；process `0xd544c0` 直接 `ret 8`。本轮不能把字段命名为“目标等级”，也未发现它负责刷新人物属性。SRefreshUserExp `0xc000d` 是另一个 BE64 经验余额通路，见 [TASK_REWARD_SOURCES.md](TASK_REWARD_SOURCES.md)；大经验余额不应塞进 float32 属性 map。

## 接线决定、验证与未知

采用 research：从原配置 ID、原生 codec、普通 handler、人物 getter 四段交叉核验；核心字段已有直接客户端证据，因此本轮不再用攻略补充或替代原生字段事实。所有新结论只适用该本地映像；没有声称覆盖其他端游版本或手游。

采用 codebase-design：建议将“已提交人物属性快照→原生属性键/RoleDetail槽位”集中在协议 **Adapter**，向成长 **Module** 保留读取显式 profile 的小 **Interface**。业务层无需学习 float32、伤势640或内嵌 vtable 偏移；同一快照提供入场和动态刷新，维持 **Locality**。未实际修改任何 Module 或生产接线。

已验证：两张原配置的CRC/长度与目标行；上述普通协议的静态序列化、解码、处理分支和列明的 getter 调用。父任务负责通用 codec 的离线原生执行验证，本轮没有重复执行，也没有把本报告标为客户端实测通过。

编码限制：float32 对整数的连续精确范围到2^24；更大整数可能舍入，NaN/Infinity及转整数溢出的业务处理未确认，不能把 map 当64位账本。RoleDetail 数值槽为 signed32，五维为 signed16；这些是编码/读取约束，不是原版业务上限。

未验证：真实客户端收到动态更新后的最终视觉结果、完整 observer 注册、面板重绘时序、战斗中同包行为、极值/负值的业务合法性、伤势规则、出生基线、自动恢复HP/MP、每级发放潜能、1000段业务及完整原服属性算法。**没有用 battle 初始化路径证明任何普通世界结论。**
