# MissionType58 等级等待任务：原客户端证据

日期：2026-10-23。范围：本地 1.6.1 / 网络版本 601 原客户端资源与原映像，只读研究。本文没有接入生产代码、运行当前客户端、在线服或战斗。

## 可以直接采用的结论

1. **原表的 MissionType58 共 30 条，不能统一等同于角色等级条件。** 其中 28 条有明确“提升至 N 级 / 历练到 20 级”文字，N 与 `MinLevel` 一致；209302 明确要求账号绑定手机；224302 没有目标文字，不能仅凭 `MinLevel=1` 自动完成。[资源 S1，全表见下]
2. **27 条含 `$number$` 的等级任务，跟踪文字的通用 Number 参数来自任务 bean 的 `value1`，本段并不直接读角色等级。** 第 28 条 203202 使用固定“20级”文字。若恢复服希望显示可信当前角色等级，需要自行写入/刷新 `value1`；“自动随角色等级显示”未获原生支持。[原代码 N3]
3. **`SRefreshState(state=1)` 自带原完成显示处理。** 原 handler 先检查本地配置的完成对白；没有完成对白、`NoteInfo` 非空时，直接调用原提示函数。不需要另造 Note 提示消息。102061、102095 的非空 Note 符合此路径；102602 有完成对白，并带动画 ID 60018，不能假设完成它没有原演出。[S1、N4、小探针 P1]
4. **`CRequestReward(0xc4a87)` 目前证据属于 HHCZY 活动界面领取路径，不是任务等级达标的通用请求。** 不能把它的一个 i32 字段直接解释成 ScenarioQuest ID 并接入任务结算。[N5]
5. 尚未找到“角色升级 → type58 条件比较 → 自动发送任务完成”的原客户端调用链，也没有原服务端规则。本批支持恢复服在可信角色等级事件上完成已激活的明确等级任务，但该触发和 `current_level >= MinLevel` 比较应记为 **inferred / designed**，不能写成已经复原原服代码。[N1、N2 的范围限制]

## N2：已接任务允许低于目标等级显示

既有协议 `SAcceptScenarioQuest=0xc4a45` 的 bean 为网络序 `i32 quest_id, i32 state, i32 value1, i32 value2, u64 npc_key`。原解码在 `0xdd8820`，Process `0x125d5c0 → 0x125d070`。所定位接收/存入路径不按配置 MinLevel 拒绝任务，也不从当前角色等级生成 value1。

因此服务端可以先同步等待中的 state2 任务，随后在等级变化时更新进度；若服务端把 MinLevel 无差别作为所有任务的领取下限，就会阻断本表“提升至 N 级继续”的等待流程。但**专用 `wait_level` 激活政策属于恢复服设计**，不是原客户端为该模式命名或原服许可逻辑的证据。其他任务的领取等级、Max155、前置和分支不能因此一并放松。

本批没有证实 type58 必须使用 state3，也没有证实客户端自行发 `CCommitScenarioQuest` 来领取等级任务奖励；不应为了显示等待进度伪造这类交互包。

## N3：跟踪 Number 取 value1，不直接取角色等级

原通用跟踪格式化路径 `0x160c770`（本段 config 参数在 `[ebp+0x70]`，UI 参数在 `[ebp+0x6c]`）：

| VA | 所见行为 |
|---:|---|
| 0x160c770 起 | 读取 config+0x238 的 TaskInfoTraceListA |
| 0x160c7xx | 使用原字符串 0x229b8c4（`$`）检查模板是否含占位符 |
| 0x160c7d9 | 读取 config.id |
| 0x160c7e2 | 调 `0x1257ac0` 查对应 ScenarioQuestInfo |
| 0x160c7f9 | 推原参数名字符串 0x228aa7c：`Number` |
| 0x160c80b | `mov eax,[edi+0xc]`，取 bean.value1 |
| 0x160c81f | 调 `0x809e90` 将数值加入格式参数 |
| 0x160c884–0x160c888 | 传入本地 trace 模板，调 `0x80ac50` 展开 |
| 0x160c8a7 | 调 `0x5200a0` 写显示文字 |
| 0x160c8ce–0x160c920 | 无占位符路径直接复制本地文字 |

本段没有读取角色等级，也没有用 bean.value2 作为目标等级。目标 N 已在模板中写死。原参数键是大写 `Number`，原资源占位符是小写 `$number$`；本批没有独立审查展开器的大小写实现，保留二者原文，不以自行拼接文本替代。

已有原进度下行 `SRefreshScenarioQuestValue=0xc4a49`：`i32 quest_id, i32 value1, i32 value2`，Process `0x1258c90` 更新 bean 的 +0xc/+0x10 并通知观察者（`0x10907c0`）。字段是更新值；不应把它编码成“本次增加等级”。

**可用于接入的最小建议（inferred / designed）**：服务端以权威等级快照将 value1 设为当前等级，再通过已有 accept/value codec 同步；value2 的 type58 特殊语义未证实，不把它自行填成 MinLevel。等级判断和完成仍由角色所有者负责，不把客户端展示字段当作资产或结算事实。

## N4：state1 的 NoteInfo 与本地完成对白

原下行 `SRefreshState=0xc4a47`：`i32 quest_id, i32 state`。调用链：`0x125ea00 → 0x125e660 → 0x125c020`。

- `0x125c0f2` 比较状态 1，`0x125c0f5` 写 bean+8；随后 `0x125c105` 调 `0x125bb30` 处理活动任务移除，更新 NPC/列表等显示。
- `0x125c168` 检查 config+0x304 的完成对白 vector 是否非空；非空时转入完成对白显示（调用 `0x164beb0`）。本批没有运行完整对白 UI。
- 完成对白为空时到 `0x125c1a2`，比较 `[esi+0x94]`（NoteInfo 长度）是否为 0。
- 非空时 `0x125c1ab` 读取 GUI 实例 `[0x2944554]`，传 config+0x80 与 `1,1,1`，`0x125c1be` 调 `0x156d130` 显示提示。
- NoteInfo 也空时，`0x125c1c5` 传 config，调用 `0x1255e70` 的后续处理。

这说明完成提示和对白由原任务配置驱动。`SAccept(state2)` 的接收路径未见此 NoteInfo 提示；不能把完成 Note 误说成接取时会自动显示。

### P1：必要的局部探针

Unicorn 仅执行原 `0x125c1a2` 至 `0x125c1cd`，synthetic config=0x5001000，manager=0x5002000，stack=0x500f000；设置 `[0x2944554]` 为 synthetic manager，在原两个被调函数入口读取栈参数后模拟返回：

| NoteInfo 长度 | 原代码走到的调用 | 观察到的参数 |
|---:|---:|---|
| 0 | 0x1255e70 | config=0x5001000 |
| 18 | 0x156d130 | config+0x80=0x5001080, 1, 1, 1 |

两个用例都在小于 100 条指令预算内到达局部终点。它只确认该分支与参数，没有证明真实 UI 生命周期、文本排版、动画行为、后继激活或完整 state1 handler 的所有前置条件。未扩大模拟，也未启动当前客户端。

## N5：CRequestReward 不是已证实的任务等级领取请求

`CRequestReward` RTTI/vtable `0x227dc50`；构造 `0xdd6fd0` 写 type `0xc4a87`；marshal `0xe57940` / unmarshal `0xdd7070`，body 为一个 i32。**结构只证明一个整数，不能独立证明是任务 ID。**

在原映像 vtable 交叉引用中，除构造/解码/框架克隆外，找到的 UI 发送使用点为 `0x124ea3e`，所在函数 `0x124e930`：

- 读取界面对象的选中行 `+0xcc`、页码 `+0xc4`、列表 `+0xb4`，以 `page*10+selected_row` 取活动行；`0x124e9b4` 调 `0x124b520`，随后复制该行。
- `0x124ea3a` 一带建立上述包，body 来自选中活动行的 ID，`0x124ea6b` 发送。
- 同一界面邻接函数 `0x124e810` 发送 `CRequestHHCZYInfo=0xc4a85`，vtable `0x227dbf8`；复制活动行中使用 `HhczyParams`，vtable `0x227e5e8`（`0x124e7dd`）。

据此，本批把这条链标记为 HHCZY 活动界面的奖励请求。没有发现该使用点将 ScenarioQuestInfo.id 或 MissionType58 ID 作为 body；不推断 HHCZY 活动中文全名，也不借此伪造任务奖励请求。静态引用扫描不排除其他间接路径，不能宣称绝不存在任务使用，但不足以开放该入口。
