# 人物潜能分配请求的原生接线研究

2026-10-23；本地端游 1.6.1 / 网络版本601。已重读 [DESIGN_AUTHORITY.md](../DESIGN_AUTHORITY.md)，沿用 research 与 codebase-design。本轮仅写本报告；不改运行时/配置，不启动、操作、注入或发包客户端，不运行战斗及升级 codec 测试。

## 可直接交接的结论

**`client_verified`：人物请求是 `CAddPointToAttr@gsp@knight`，type `0xc000c`，payload 固定20字节，五个非负大端 i32。其顺序为体质、内力、力量、敏捷、耐力，即属性 ID `[10,20,30,50,40]`。最后两项与常用五维顺序相反。**

五项都是**本次分配增量**，不是最终五维、剩余潜能或分配比例。原人物界面先把暂存增量加到当前五维作预览，再按上述顺序提交，发送后将五项和暂存合计清零。请求里**没有 roleid、版本、nonce、剩余潜能或确认标志**；不能为接原生客户端而额外要求这些 payload 字段。服务器如何识别角色、验证当前余额和串行提交属于会话与角色事务 Interface，不能从这20字节取得。

## 一手来源

离线映像 [native-image.bin](native-image.bin)，BASE `0x400000`，SHA-256 `2b49e95d27cbbec0d83a049b5495da4365b205d9a913582b1e6688df67468791`；本报告地址均为该映像 VA。用 [native_inspect.py](../native_inspect.py) 只读 RTTI、vtable、原编解码和人物 UI 路径。没有重新采集进程，也没有用宠物请求替代人物请求。

本轮用 [pfs.py](../pfs.py) 直接读原 `artres/ui.pfs`、校验本地/目录头、长度和 CRC 后 BXML 解码：`layouts/characterproperty.layout`，89355字节，CRC32 `837d9612`，SHA-256 `9981f285f453462e0c30559bc9d523ed6bcb63c6c39547f61982de9707a44a71`。其中 `CharacterPropertyDlg/confirmBtn` 类型为 `TaharezLook/LittleButton`，Text=`确定`。

人物属性名字/ID由此前已直接CRC核验的 `artres/config.pfs → autoconfig/knight.gsp.item.cattributedesconfig.xml` 提供：10体质、20内力、30力量、40耐力、50敏捷、500潜能点。原包19508字节、CRC `56e2ca7e`，具体人物 getter 消费证据见 [ROLE_GROWTH_UI_RESEARCH.md](ROLE_GROWTH_UI_RESEARCH.md)。

## 请求类型、字段与约束

RTTI `.?AVCAddPointToAttr@gsp@knight@@` 地址 `0x2885474`；vtable **`0x226f924`**。这与 `CAddPetPoint@pet` 不是同一类或同一消息。

| 项目 | 原生 VA 与确定行为 |
|---|---|
| 默认构造 | `0xd4e0e0`；`0xd4e0e4`写vtable，`0xd4e0ea`写type **`0xc000c`**；object+8/+c/+10/+14/+18全部默认0 |
| 字段 validator | `0xd4e110`；逐一检查五项有符号整数 >=0；无总和、余额、单属性成长上限检查 |
| marshal | **`0xe3f940`**；重复非负检查，再按+8/+c/+10/+14/+18调用`0x770960`写五个BE32；没有其他字段或集合头 |
| unmarshal | **`0xd4e1b0`**；每项读4字节、`bswap`，依次写+8/+c/+10/+14/+18；`0xd4e2ed..0xd4e31e`做同样非负检查 |
| 客户端 process | `0xd4e160`直接`ret 8`；这是上行请求，不是属性刷新下行 |
| vtable+0x10函数 | `0xd4e140`以传入值与`0xffff`比较；本轮不把该通用长度/策略入口冒充“五项各最多65535” |

| wire序号 / payload偏移 | 请求对象偏移 | 人物UI暂存来源 | 已确认的属性与语义 |
|---|---|---|---|
| 1 / +0 | +8 | UI+0x16c | 体质10的本次增量 |
| 2 / +4 | +c | UI+0x170 | 内力20的本次增量 |
| 3 / +8 | +10 | UI+0x174 | 力量30的本次增量 |
| 4 / +12 | +14 | UI+0x17c | **敏捷50**的本次增量 |
| 5 / +16 | +18 | UI+0x178 | **耐力40**的本次增量 |

如果内部 Interface 采用 `(体质,内力,力量,耐力,敏捷)`，协议 Adapter 必须交换 wire 第4/5项。codec按有符号整数判非负，因此字段可表示范围是0..2147483647；这是编码限制，不是原版业务允许一次分配这么多。五项全0能通过该原生字段 validator，但不能据此断言原服零请求有实际效果。

## 人物“确定”按钮到发送的链路

1. native字串 `0x22928f8 = CharacterPropertyDlg/confirmBtn`。`0x11550ed..0x115513c` 通过该路径取控件，存到人物 UI+0x88。
2. `0x115521b` 建回调，函数地址 **`0x114e620`**、对象为本人物界面；`0x1155239..0x115525e` 在 UI+0x88 控件注册该回调。原资源的同名按钮文字是“确定”，因此不是只凭 `CAddPointToAttr` 类名猜测入口。
3. 提交处理 **`0x114e620`** 在 `0x114e674..0x114e68c` 检查全局对象+0x54及`0x813830()`返回对象+0x1ed的状态，若命中跳至提示分支，不发送分配请求。该分支 `0x114e6a7`引用消息 **140634 / `0x2255a`**；本轮直接解码原 `config.pfs → autoconfig/knight.gsp.message.cmessagetip.xml` 对应行：**“战斗或小游戏中不能分配潜能点。”** 可确认合并资格限制，两个低层状态各对应哪个场景不再猜名。
4. 正常分支 `0x114e6cc`在栈上放vtable，`0x114e6d4`放type `0xc000c`；`0x114e6dc..0x114e70e`把五项暂存值按上表顺序写入请求，未从当前属性 getter读取最终五维或roleid。
5. `0x114e712`取连接管理对象，`0x114e717..0x114e723`通过vtable+0x3c发送该栈请求。
6. `0x114e725..0x114e745`把UI+0x16c/+170/+174/+178/+17c以及UI+0x180全部清零。这里只证明客户端清暂存；没有证据把它当服务器已成功落账的确认。

## 为什么能确定是“增量”

人物预览函数 **`0x1150fb0`** 从人物全局`0x2944550`取属性对象`role+0xf8`，通过`0x108f340`读取**已存在五维**，再逐项相加 UI暂存值：

| 预览getter调用 | getter key | 随后的相加 |
|---|---:|---|
| `0x1151061` | 10 | `0x1151066 add eax,[UI+0x16c]` |
| `0x11510d6` | 20 | `0x11510db add eax,[UI+0x170]` |
| `0x115115a` | 30 | `0x115115f add eax,[UI+0x174]` |
| `0x11511de` | 40 | `0x11511e3 add eax,[UI+0x178]` |
| `0x1151262` | 50 | `0x1151267 add eax,[UI+0x17c]` |

同函数`0x1151340..0x1151354`以 key500读取人物潜能，再减UI+0x180作**剩余潜能预览**。所以+0x180是本次已暂配合计，既不是第六个网络字段，也不能将五项解释为“各自分配后的剩余值”。

加减暂存函数 **`0x1151ec0`** 提供第二条佐证：`0x1151ed1..0x1151ed6`取人物潜能500；增加分支`0x1151ee6..0x1151eee`在暂配合计>=人物潜能时返回。`0x1151f74..0x1151f7f`将选中暂存项和合计同时+1；另有每次最多5点以及一次使用所有余点的布尔参数分支，未追对应鼠标/键盘修饰键名称。减少分支从选中暂存项和合计减同样的值，不会把现有人物基础五维减掉；`0x1151ffe..0x1152003`是每次减1。`0x115200a..0x115201b`仅当暂配合计非0时启用 UI+0x88“确定”，再调用预览函数。

这三段链路——**现有属性+暂存预览、潜能−暂配合计、只发送并清零暂存**——已经足够静态确认“增量”，无需依靠网页或其他游戏协议。

## 方法、决定与未验证范围

research实际用于 RTTI→请求codec→人物按钮注册→预览/余额三段一手交叉核验，并直接核验原UI资源和相关消息文本；字段语义已闭合，本轮没有引入手游或另版攻略。

codebase-design实际影响交接决定：把 wire顺序`[10,20,30,50,40]`、固定20字节与字段非负限制收在协议 **Adapter**，保持内部成长 **Module** 的既有五维 **Interface** 顺序；角色身份、余额和提交版本在会话/角色事务 **Seam** 处理，原生包没有的字段不能由客户端凭空提供。暂配值与服务器已提交快照分开，避免把一次发送后的客户端清零作为账本确认。这些是接线建议，本轮未修改实现。

已验证：静态原codec及全部五项偏移/顺序/约束、人物确认按钮绑定、预览的增量相加、人物潜能500减合计、提交与清暂存。原版服务器如何判总和、是否允许全0、上限、扣点/派生计算/回包时序、重复包是否会重复分配、断线重试策略均未从客户端20字节中证明；须由当前主策划与角色状态所有者明确设计，不能虚称原版幂等协议。

未验证：真实客户端操作效果、离线原生执行此请求codec、服务器端实现或手工加点现场；没有进行任何在线测试。与升级`CReqLevelUp 0xc32cd`、普通属性刷新`SRefreshRoleData 0xc32c8`分开：本请求只表达增量意图，成功后最终五维、潜能500及派生/maxima的下行可沿 [ROLE_GROWTH_UI_RESEARCH.md](ROLE_GROWTH_UI_RESEARCH.md) 的普通刷新通路接线。
